# 偏好记忆与对话恢复

## 用户可见行为

- “记住，我喜欢无糖饮料，也爱吃薯条”：记录明确口味。首次可以没有门店。
- 没有内置套餐昵称映射。选店后说“昵称就是菜单中的餐品名”，或点餐时说“我要某餐品（即我的昵称）”；仅核实唯一目标后保存，来源为用户定义。简称有多个匹配时请用户选择，目标缺货不得换成其他套餐。昵称可以覆盖纠正，也可以在手记或聊天中忘记。菜单价格和官方算价各自展示。
- “今天要普通可乐”：本次要求优先于无糖默认，不反过来永久修改习惯。
- “我的偏好”“忘记无糖”“清除偏好”“关闭记忆”“开启记忆”：随时管理，不触发订单操作。
- 餐品被多次明确选择后形成较弱的推荐信号，标明“选择次数”，不冒充付款或消费次数。

## 保存范围

`scripts/dining_memory.py` 使用项目 `runtime/dining-memory.sqlite3`，权限600，以操作者散列隔离。保存有限的饮食标签、已验证目标的自定义别名和餐品选择统计。模型不能直接改记忆。不保存完整聊天、精确位置、账户ID、卡包券码、手机号、健康情况或凭证；不读取官方常点画像或历史订单。测试使用各自临时确认库旁的独立偏好库。

微信和网页的操作者分别隔离，不通过猜测把网页访客合并为绑定微信。微信页的管理操作明确针对当前绑定者。

原版对话上下文漏掉助手回复、快捷命令及按钮操作。现改为每次会话保存最近8条用户/助手上下文、当前已选餐品和待补充城市的查询。只在内存中维护最近20轮脱敏对话；微信页按需查看，重启清空，无法补读以前没有存储的聊天。账户查询结果不放进模型上下文。

## 已复现错误与恢复

门店查询失败后，旧版对话可能只返回模型生成的重试承诺，却没有实际查询结果。以下仅描述错误机制，不保留个人故障对话或真实地点。

`query-nearby-stores` 只带 `searchType=2/beType=1/keyword`、缺少city时可能返回 `success=false, code=600058`；补充有效城市后再查询候选。虽然实时 schema 未将city列入required，客户端必须补齐城市。缺失时只追问城市并保留想吃的餐品，用户回复城市后实际执行查询。测试使用合成门店名“示例广场店”。

`OrderingAgent._query` 区分查询阶段，记录有限的待重试只读操作。“重试”真正执行该查询；不自动循环、不重放写请求。模型的question里出现“我帮您重新查”等未执行承诺时采用本地澄清文案。所有下单仍受当前预览和确认台账约束。

## 麦当劳账户

MCP Token 来源于官方平台登录/激活后的授权账号，个人微信扫码只是消息入口。有效Token通常不用在本地重复登录；付款页可另要求验证。切换微信不等于切换麦当劳账号，变更麦当劳账号需更新相应Token。

“账号说明”只解释机制，不读取资产。“我的积分”调用 `query-my-account`；“我的优惠券”调用 `query-my-coupons`，只展示必要信息，不显示账户ID和券码，不声称卡包券必然适用于当前门店。已发现的工具中没有用于取得完整个人资料/手机号/会员等级的专用工具。公开测试仅使用模拟账户，不包含个人资产与账户标识。

## 界面约定

沿用现有红色 #C82028、黄色 #FFBC0D、纸白 #FFFFFF、浅灰 #F4F5F7 与墨色 #242424，中文系统字体。微信页保持原连接流程，下面以现有设置分区展示偏好摘要和管理按钮；最近对话折叠在同一区，不另造第二个点餐入口。手机改为单列，长文本可断行，所有对话用textContent渲染。

本机后台的 `/api/weixin/recent` 只返回当前绑定者的内存对话和偏好；`/api/weixin/memory` 必须经过本机来源校验，只支持启用、停用和清除。公开定位监听器不开放这些路由。

## 麦合拍的反馈与陪伴层

`preferences` 表仍以同一操作者散列作为键，旧JSON缺少的新字段通过默认值兼容读取，不复制或合并用户身份。`evidence` 保存明确饮食标签的来源、极性和更新时间；`last_selection` 只保存最近真实选择的餐品名、随机选餐标记和时间。它不是订单或付款记录。

`feedback` 最多30个餐品，每个最多10次选餐评价；同一选餐标记的评价可修正且仅计一条。仅记录好吃/一般/不喜欢三个枚举，不保存原始评语。明确指代本餐的非疑问、非假设表述可触发反馈；网页按钮必须带当前选餐标记，旧标记拒绝。`insights` 在读取时由最近90天评价计算，时间越久影响越小；明确喜好不因一次反馈改变。单项忘记会删除相应明确喜好、选择、反馈和最近选餐；清除全部和停用覆盖新增层。数据库更新启用SQLite secure_delete，控制只面向本项目当前数据库，不承诺清除用户自行制作的外部备份。

模型读取必要的偏好摘要与当前会话，不能直接修改记忆。关闭记忆时模型上下文只得到enabled=false，旧偏好不会继续作为默认输入。闲聊返回受schema验证的chat意图，不改数量、搭配或确认；业务成功描述、价格、付款链接仍由实际工具结果负责。未配置模型时保留明确指令和本地招呼，不冒充自由对话。

本地排序合并真实菜单、明确需求、明确喜好、重复选择、近期反馈和模型建议；模型顺序只是较弱的参考。各推荐给出可核对的理由。口味复盘是有证据的确定性汇总，模型可以围绕摘要交流，不宣称在线训练、拥有身体或主动联系其他人。网页和微信记忆仍隔离；聊天全文、情绪原文、精确位置、账户资产和联系人不进入长期手记。

## 餐品身份与昵称修复

套餐昵称不再预置或按系列合并。服务端先在当前门店完整菜单中匹配用户本轮具体名称，支持唯一的名称简称；完整名称优先于含有它的其他商品，简称有多个SKU时仅列匹配项，用户再选择。模型输出的旧推荐序号和产品编码不能覆盖本轮明确名称。指定商品是候选约束，长期喜好、套餐关键词加分和模型排序均不能把它换成其他套餐。

用户明确的“昵称就是餐品名”和“我要某餐品（即昵称）”经当前菜单唯一目标验证才进入aliases，alias_evidence记录user_definition来源和时间；模型不写入别名事实。没选店、目标不明或记忆关闭时不保存。覆盖定义可纠正；忘记、清除、关闭覆盖昵称层。旧资料保留，不再将旧系列标签推断为某个真实SKU；已学昵称在新门店缺少原目标时不得替换成相似商品。

完整菜单匹配不受模型前200项上下文限制；本轮目标优先进入模型上下文。取消选餐和明确纠错会使旧确认失效，具体SKU选择、搭配和价格仍由官方查询验证。回归测试仅使用合成门店与模拟数据；真实菜单核验只查询，没有创建订单或发送微信消息。
